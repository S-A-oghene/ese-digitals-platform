# Ese Digitals G9.6 — D1 Free-First Implementation

## Purpose

Move the public Opportunity Intelligence execution/data boundary off the Apps Script web-app endpoint and onto Cloudflare Workers + Cloudflare D1 while preserving the Phase 4 trust model and the existing public Opportunity contract.

The private PDE_OS_MASTER remains the private business/control plane. D1 is the public-safe Opportunity Intelligence store.

## Architecture

```text
Browser
  -> same-origin /api/opportunities
  -> Cloudflare Worker
  -> G9.6 Worker-native engine
  -> D1
      -> jobs
      -> job_sources
      -> job_evidence
      -> user_profiles
  -> public-safe results
```

Apps Script remains available for the broader PDE OS functions (CRM, Gmail, Drive and internal automation) but is no longer required for the public Opportunity Engine request path.

## Free-tier safety policy

The system must remain $0 until the owner deliberately chooses an upgrade.

Guardrails implemented at application level:

- maximum 100 D1 candidate rows considered per search;
- maximum 20 public results per search;
- parameterized SQL only;
- no public write endpoint for the opportunity database;
- no per-search external-source fan-out;
- indexed/FTS retrieval instead of unbounded table scans;
- no private CRM, finance or audit data in public responses;
- no automatic job applications;
- explicit Worldwide permission remains required;
- empty database is a valid state and must not be filled with fabricated jobs.

Cloudflare's current Workers Free limits include 100,000 Worker requests/day. D1 Free currently includes 5 million rows read/day, 100,000 rows written/day, 500 MB maximum database size, 5 GB total account storage, 50 D1 queries per Worker invocation, and 7 days of Time Travel. See the current Cloudflare documentation before changing the production plan.

## Capacity behavior

When a D1 daily read/write allowance is exhausted, the Worker should fail safely with a controlled `SERVICE_UNAVAILABLE` response rather than attempting paid fallback services.

When storage becomes full, ingestion should stop and the system should preserve existing data until an owner performs cleanup or explicitly upgrades.

## Data trust rules

The database must contain only real records from approved sources or deliberately verified manual seeds.

The Phase 4 Manual requires: discovery -> normalization -> verification -> deduplication -> eligibility -> matching -> ranking -> action -> measurement -> learning.

The public layer must not imply that Remote means Worldwide or Nigeria-eligible, and a match score must not be presented as legal eligibility.

## Database objects

### JOBS

The 35-field revised schema is implemented in `migrations/0001_phase4_opportunity_core.sql`:

`Job_ID, Source_ID, Source_Type, Source_Name, Title, Company, Department, Role_Family, Description, Location, Remote_Type, Eligible_Countries, Eligible_Regions, Excluded_Countries, Work_Authorization, Timezone, Employment_Type, Salary_Min, Salary_Max, Currency, Posted_Date, Updated_Date, First_Seen, Last_Verified, Application_URL, Source_URL, Active, Eligibility_Status, Eligibility_Reason, Freshness_Status, Verification_Status, Content_Hash, Match_Keywords, Created_At, Updated_At`

### JOB_SOURCES

Stores source identity, endpoint metadata, enablement and verification rules.

### JOB_EVIDENCE

Stores the evidence chain supporting source, eligibility, remote and freshness claims.

### USER_PROFILES

Reserved for future profile/alert functionality. Public search requests do not write profile data.

## D1 bootstrap

From the repository root on Windows:

```cmd
npx wrangler d1 create ese-digitals-opportunities --binding OPPORTUNITY_DB --use-remote --update-config
npx wrangler d1 migrations apply ese-digitals-opportunities --remote
```

The first command creates the remote D1 database and updates `wrangler.jsonc` with the binding/database ID. The second applies the versioned SQL migration.

Do not hand-edit a placeholder database UUID into `wrangler.jsonc`.

## Verification

After migration:

```cmd
npx wrangler d1 execute ese-digitals-opportunities --remote --command="SELECT name FROM sqlite_master WHERE type IN ('table','view') ORDER BY name;"
```

Expected core tables include `jobs`, `job_sources`, `job_evidence` and `user_profiles`.

Before seeding data, verify that the public website returns a controlled empty result rather than fabricated records.

## Permissions

No database credential is placed in GitHub or frontend code. D1 access is provided to the Worker through the `OPPORTUNITY_DB` binding. Administrative data-writing operations, when added, must use a separate authenticated path and must never be exposed to ordinary website visitors.

The `src/` and `migrations/` directories are implementation assets and are excluded from static asset publication via `.assetsignore`.
